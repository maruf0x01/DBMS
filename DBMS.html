1.1 File System vs Database Management System (DBMS) 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনের শুরুর টপিক: "file system vs DBMS (Different) characteristic"। প্রতি বছর এখান থেকে সরাসরি পার্থক্য বা ফাইল সিস্টেমের সীমাবদ্ধতা (Drawbacks of File Systems) ৫ থেকে ৮ নম্বরের প্রশ্ন হিসেবে আসে।

সহজ বাংলায় কনসেপ্ট (Beginner Explanation)

চলো আগে বুঝি জিনিসটা আসলে কী:
আগেকার দিনে কম্পিউটারে ডেটা রাখা হতো সাধারণ ফাইল বা এক্সেল ফাইলের মতো টেক্সট ফাইলে। যেমন ধরো, ভার্সিটির একাউন্টস সেকশন স্টুডেন্টের নামের তালিকা একটা ফাইলে রাখল, আবার লাইব্রেরি সেকশন আরেকটা ফাইলে রাখল।
এখন সমস্যা কী?
১. একাউন্টসে ফোন নম্বর আপডেট করলে লাইব্রেরির ফাইলে তা পুরনোই থেকে গেল (Data Inconsistency)।
২. একই নাম দুই ফাইলে বারবার লেখা হলো (Data Redundancy)।
৩. ব্যাংক একাউন্ট থেকে টাকা ট্রান্সফারের সময় মাঝপথে বিদ্যুৎ চলে গেলে একাউন্ট থেকে টাকা কাটবে কিন্তু অন্য একাউন্টে জমা হবে না (Atomicity Problem)।
DBMS হলো এমন এক সেন্ট্রালাইজড সফটওয়্যার, যা এই সব সমস্যার স্থায়ী সমাধান করে ডেটাকে সুরক্ষিত, নিখুঁত এবং একই সাথে হাজার হাজার ইউজারের জন্য ব্যবহারযোগ্য রাখে।
Formal Definition (Source: 1.1Introduction.pdf, Page 2)
"A Database Management System (DBMS) consists of a collection of interrelated data and a set of programs to access that data. DBMS provides an environment that is both convenient and efficient to use."
Key Terms to Remember: Interrelated data, Access programs, Convenient, Efficient, Enterprise information.

স্লাইড অনুযায়ী ফাইল সিস্টেমের ৭টি মারাত্মক সীমাবদ্ধতা (Drawbacks of File Systems)

Source Material (1.1Introduction.pdf, Pages 3–4) অনুযায়ী ফাইল সিস্টেমের মূল সমস্যাগুলো নিম্নরূপ:

  1. Data Redundancy and Inconsistency: Multiple file formats and duplication of information across different files lead to higher storage costs and conflicting data when updates happen.
  2. Difficulty in Accessing Data: Users must write a brand-new application program to carry out every newly requested task or ad-hoc query.
  3. Data Isolation: Because data is scattered in various files with different formats, writing new application programs to retrieve matching data is extremely difficult.
  4. Integrity Problems: Integrity constraints (e.g., account_balance > 0) become hardcoded directly inside program code. It is very hard to add new constraints or modify existing ones.
  5. Atomicity of Updates: Failures (power cut, OS crash) may leave the database in an inconsistent state with partial updates carried out. (e.g., Transfer of funds must either complete 100% or not happen at all — "All-or-Nothing").
  6. Concurrent Access Anomalies: Uncontrolled concurrent access by multiple users reading and updating the exact same record at the same time leads to corrupted, inconsistent data.
  7. Security Problems: Enforcing granular access control (e.g., financial clerk seeing balance but not manager passwords) is extremely hard in traditional file systems.

Q1: Why is atomicity important in database transactions? Give an example from banking.

Model Answer for Exam

Definition: Atomicity is the "all-or-nothing" property of a transaction, ensuring that either all operations of the transaction are executed successfully or none are.
Why Needed: If a system crash occurs midway through an execution, the database must not be left in a partially updated, inconsistent state.
Banking Example (from PDF 1, Page 4): Suppose Customer A transfers $500 to Customer B. This involves two steps: (1) Deduct $500 from Account A, and (2) Add $500 to Account B. If power fails immediately after step 1, Account A loses $500 while Account B never receives it. A DBMS guarantees atomicity by rolling back step 1, leaving the database completely consistent.

Q2: How does a DBMS handle integrity constraints compared to a traditional file system?

Model Answer for Exam

In a file processing system, integrity constraints (e.g., balance > 0) are hardcoded inside individual application programs. If a new business constraint is added, programmers must locate and modify every application program accessing those files. In contrast, a DBMS enforces integrity constraints centrally within the database schema using DDL statements (e.g., CHECK(balance > 0)). The DBMS engine automatically validates all incoming insert/update operations regardless of which application submits them.

1.2 Three Levels of Data Abstraction 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে স্পষ্টভাবে চিহ্নিত: "Abstract level"। পরীক্ষায় "Explain the 3 levels of data abstraction with an appropriate architecture diagram" প্রশ্নটি প্রায় নিশ্চিতভাবে আসে।

সহজ ভাষায় কনসেপ্ট (Beginner Explanation)

চলো আগে বুঝি জিনিসটা আসলে কী:
তুমি যখন কোনো ব্যাংকের অ্যাপে ঢুকো, তুমি শুধু তোমার নাম আর একাউন্ট ব্যালেন্স দেখতে পাও (View Level)। তুমি কিন্তু দেখতে পাও না ব্যাংকের মূল ডেটাবেজের টেবিলে আর কী কী ফিল্ড বা অন্যান্য কাস্টমারের তথ্য আছে (Logical Level)। আর সেই ডেটা হার্ডডিস্কের কোন মেমোরি ব্লকে, কোন B-Tree ইনডেক্সে বাইনারি আকারে রাখা আছে—তাও তোমার জানার দরকার নেই (Physical Level)।
এই যে অপ্রয়োজনীয় টেকনিক্যাল জটিলতা গোপন রেখে ইউজারকে সহজ ইন্টারফেস দেওয়া—একেই বলে Data Abstraction!
Formal Definition (Source: 1.1Introduction.pdf, Page 5)
"A major aim of a DBMS is to provide users with an abstract view of data. Data Abstraction hides certain details of how the data are stored and maintained, using several levels of abstraction to simplify users' interaction with the system."
Key Terms: Hide complex storage details, Levels of abstraction, Physical level, Logical level, View level.

Detailed Explanation of the 3 Levels (Source: 1.1Introduction.pdf, Page 6)

  • 1. Physical Level (Lowest Level): Describes how a record is actually stored physically on storage media (e.g. magnetic disk, SSD). It involves complex low-level data structures, file organizations, block sizes, and access paths (record offsets, B+ trees, hashing).
  • 2. Logical / Conceptual Level (Middle Level): Describes what data are stored in the entire database and what relationships exist among those data. The entire database is described in terms of relatively simpler logical structures (e.g., relations, schemas, records). Database Administrators (DBAs) work at this level to decide what information to maintain.
    type customer = record
      name: string;
      street: string;
      city: string;
    end;
  • 3. View Level / External Level (Highest Level): Describes only part of the entire database relevant to a specific group of users. Many distinct views can exist for the same database. Application programs hide implementation details and security-sensitive information (e.g., hiding staff salaries from clerical workers).

1.3 ANSI/SPARC Architecture & Data Independence 🟡 MEDIUM PRIORITY

Source: 1.1Introduction.pdf (Pages 9–11)

১৯৭৫ সালে ANSI/SPARC (American National Standards Institute - Standards Planning and Requirements Committee) ৩-টিয়ার ডেটাবেজ আর্কিটেকচার প্রস্তাব করে। এর প্রধান উদ্দেশ্য ছিল Data Independence অর্জন করা।

Mappings in ANSI/SPARC Architecture

  • External/Conceptual (E/C) Mapping: Relates each external view to the global conceptual schema. It defines how a specific user view is derived from the conceptual schema.
  • Conceptual/Internal (C/I) Mapping: Relates the conceptual schema to the internal (physical) storage schema. It defines how logical entities and fields map to disk storage blocks and file records.
Type of Data Independence Definition & Core Concept Where Mapping Occurs Exam Example
Physical Data Independence (PDI) The ability to modify the physical schema (storage structures, indexing, file organization) without requiring changes to the logical/conceptual schema or application programs. Conceptual / Internal (C/I) Mapping Changing disk storage from sequential file to B+ Tree index, or switching hard drives, without modifying SQL queries or table definitions.
Logical Data Independence (LDI) The ability to modify the logical/conceptual schema (adding new tables, columns, or relationships) without having to rewrite existing external schemas or application programs. External / Conceptual (E/C) Mapping Adding a new column guardian_phone to a Student table without breaking existing applications that only query sid, name, gpa.

1.4 Database Administrator (DBA) Major Duties 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে সরাসরি উল্লেখিত: "DBA duty"। পরীক্ষায় সরাসরি ৪ বা ৫ নম্বরের জন্য "List and explain the main functions/duties of a Database Administrator" প্রশ্নটি আসে।

Formal Definition (Source: 1.1Introduction.pdf, Page 15)
"A Database Administrator (DBA) is a person or group who coordinates all the activities of the database system; the DBA has a good understanding of the enterprise's information resources and needs."

Slide-Mandated 7 Primary Duties of a DBA (Source: 1.1Introduction.pdf, Page 15)

  1. Schema Definition: Creating the original database schema by writing a set of data definition statements in DDL.
  2. Storage Structure and Access Method Definition: Determining how data is organized on disk, creating appropriate file structures, indices, and allocation parameters.
  3. Schema and Physical Organization Modification: Writing DDL/ALTER commands to alter the logical schema or physical storage organization to adapt to evolving enterprise requirements.
  4. Granting User Authority to Access the Database: Managing security privileges and granting authorizations so different users only see and modify data they are permitted to access.
  5. Specifying Integrity Constraints: Defining explicit data consistency rules (e.g. primary keys, foreign key relationships, check conditions) within the data dictionary.
  6. Acting as Liaison with Users: Consulting with application programmers and organizational end-users to ensure their data needs are met without conflicting with other departments.
  7. Monitoring Performance and Responding to Changes: Continuously tuning indexes, memory buffers, and disk layouts to prevent system slowdowns as database size increases.

2.1 Strong Entity Set vs Weak Entity Set 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে স্পষ্টভাবে দাগানো: "Strong Entity set vs weak entity set"। প্রতি পরীক্ষায় Weak Entity এর সংজ্ঞা, বৈশিষ্ট্য, Discriminator এবং ER সিম্বল নিয়ে প্রশ্ন থাকে।

সহজ ভাষায় কনসেপ্ট (Beginner Explanation)

চলো আগে বুঝি জিনিসটা আসলে কী:
Strong Entity: যার নিজের একটা নিজস্ব প্রাইমারি কি (Primary Key) আছে। যেমন Student(Roll_no, Name, Age)। এখানে Roll_no দিয়ে যেকোনো স্টুডেন্টকে একদম আলাদাভাবে চেনা যায়। তার অস্তিত্বের জন্য অন্য কারও ওপর নির্ভর করতে হয় না। একে সিঙ্গেল আয়তক্ষেত্র (Rectangle) দিয়ে আঁকা হয়।
Weak Entity: যার নিজের কোনো প্রাইমারি কি নেই! সে একা একা বাঁচতে পারে না; তার অস্তিত্বের জন্য অন্য একটি স্ট্রং এনটিটির ওপর নির্ভর করতে হয়।
বাস্তব উদাহরণ (স্লাইড পেজ ১ ও ২৩): বিল্ডিং না থাকলে রুমের কোনো অস্তিত্ব নেই। পিতা-মাতা ছাড়া সন্তানের কোনো স্বাধীন এন্ট্রি হতে পারে না। একইভাবে, ব্যাংক লোন (loan) না থাকলে লোন পেমেন্ট (payment) এর কোনো অস্তিত্বই থাকতে পারে না! একে ডাবল আয়তক্ষেত্র (Double Rectangle) দিয়ে আঁকা হয়।
Formal Definition (Source: 2nd Chapter-1.pdf, Page 23)
"An entity set that does not have a primary key is referred to as a weak entity set. The existence of a weak entity set depends on the existence of an identifying entity set via a total, one-to-many relationship set from the identifying to the weak entity set."
Key Terms: No primary key, Existence dependent, Identifying entity set, Identifying relationship (double diamond), Discriminator (partial key with dashed underline).
Figure 2.1: Weak Entity Set Representation with Identifying Relationship (Source: 2nd Chapter-1.pdf, Page 23)

How to form Primary Key of Weak Entity Set?

💡 FORMULA FOR WEAK ENTITY PRIMARY KEY

Primary Key of Weak Entity = Primary Key of Strong Entity + Discriminator (Partial Key)
Example: payment টেবিলের প্রাইমারি কি হবে = (loan_number, payment_number)।

Feature Strong Entity Set Weak Entity Set
Primary Key Has its own primary key that uniquely identifies each tuple. Does NOT have its own primary key; has only a discriminator (partial key).
Dependency Independent existence; does not rely on any other entity. Existence-dependent on a dominant/identifying strong entity.
ER Representation Single Rectangle. Primary key underlined with a solid line. Double Rectangle. Discriminator underlined with a dashed line.
Relationship Type Connects via standard relationship (single diamond). Connects via Identifying Relationship (double diamond).
Participation Can have either partial or total participation. Always Total Participation (double line) in identifying relationship.

2.2 DBMS Keys: Super Key vs Candidate Key (CK) 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে স্পষ্টভাবে দাগানো: "Super key vs CK"। পরীক্ষায় "Define Super Key and Candidate Key. Why is Candidate Key called a minimal super key? Explain with an example table" প্রশ্নটি নিয়মিত আসে।

সহজ ভাষায় কনসেপ্ট (Beginner Explanation)

চলো আগে বুঝি জিনিসটা আসলে কী:
ধরো তোমার ক্লাসের একটা টেবিল আছে যেখানে আছে (Roll_no, Reg_no, Name, Phone)।
• Super Key: যে ফিল্ড বা ফিল্ডগুলোর কম্বিনেশন দিয়ে একটি সারিকে ইউনিকভাবে চেনা যায়। যেমন: শুধু {Roll_no} ইউনিক। তাহলে {Roll_no, Name}-ও ইউনিক, {Roll_no, Phone, Name}-ও ইউনিক! এগুলো সবই সুপার কি। অর্থাৎ সুপার কি-র মধ্যে বাড়তি বা অপ্রয়োজনীয় (redundant) ফিল্ড থাকতে পারে।
• Candidate Key: সুপার কি-র মধ্য থেকে যখন সব অপ্রয়োজনীয় বাড়তি ফিল্ড ফেলে দিয়ে শুধুমাত্র ন্যূনতম (Minimal) সেটটুকু রাখা হয়, তাকে বলে ক্যান্ডিডেট কি।
সহজ কথায়: সব ক্যান্ডিডেট কি-ই সুপার কি, কিন্তু সব সুপার কি ক্যান্ডিডেট কি নয়! (Candidate Key = Minimal Super Key without redundant attributes).
Formal Definitions (Source: 2nd Chapter-1.pdf, Pages 8, 13)
Super Key: "A super key is a set of one or more attributes that, taken collectively, allows us to identify uniquely a tuple in the relation."
Candidate Key: "Candidate keys are selected from the set of super keys. A candidate key is a minimal super key with no redundant attributes."

Slide-Based Worked Example (Source: 2nd Chapter-1.pdf, Page 13)

লেটস কনসিডার স্লাইডের Employee টেবিলটি:

Emp_SSN Emp_Number Emp_Name
123456789226Steve
999999321227Ajeet
888997212228Chaitanya

উপরের টেবিলে Emp_SSN ইউনিক এবং Emp_Number-ও ইউনিক।

  • Super Keys of this table:
    {Emp_SSN}, {Emp_Number}, {Emp_SSN, Emp_Number}, {Emp_SSN, Emp_Name}, {Emp_Number, Emp_Name}, {Emp_SSN, Emp_Number, Emp_Name}.
    কারণ: এগুলোর প্রতিটিই টেবিলের প্রতিটি রো-কে এককভাবে শনাক্ত করতে পারে।
  • Candidate Keys:
    শুধুমাত্র {Emp_SSN} এবং {Emp_Number}।
    কেন? কারণ {Emp_SSN, Emp_Name} থেকে যদি Emp_Name বাদ দিয়ে দিই, তবুও শুধু Emp_SSN দিয়েই রো চেনা সম্ভব। তাই Emp_Name হলো একটি রিডান্ড্যান্ট (অনর্থক) অ্যাট্রিবিউট। ক্যান্ডিডেট কি-তে কোনো রিডান্ড্যান্ট অ্যাট্রিবিউট থাকতে পারবে না!
Property Super Key Candidate Key
Minimality Not necessarily minimal; may contain redundant attributes. Strictly minimal; no proper subset is a super key.
Relationship Superset of Candidate Key. Subset of Super Keys. Every Candidate Key is a Super Key.
Selection Base Any attribute set capable of unique tuple identification. Selected from super keys by removing unnecessary/redundant fields.
Role in Table Broad mathematical concept for uniqueness. Eligible candidates from which the Primary Key is chosen.

2.3 Primary Key vs Unique Key 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে স্পষ্টভাবে দাগানো: "Pk vs unique key"। পরীক্ষায় টেবিল আকারে এদের পার্থক্য চাওয়া হয় এবং NULL এলাও করে কি না তা জিজ্ঞেস করে।

Comparison Dimension Primary Key Unique Key
Purpose Uniquely identifies each record/tuple in a table and serves as the primary target for foreign key references. Ensures that all values in a specific column or group of columns are distinct from one another.
NULL Acceptance NEVER accepts NULL values. (Must be NOT NULL by definition). Accepts NULL values. (Allows one NULL in standard SQL, or multiple NULLs depending on DB engine).
Number of Keys per Table A table can have only ONE Primary Key. A table can have multiple Unique Keys.
Index Creation Automatically creates a Clustered Index by default (physical storage order matches PK). Automatically creates a Non-Clustered Index.
SQL Syntax Example id INT PRIMARY KEY or PRIMARY KEY(roll) email VARCHAR(50) UNIQUE or UNIQUE(phone)
⚠️ COMMON MISTAKE TO AVOID

পরীক্ষায় অনেকে লেখে: "Unique key cannot have NULL". এটি সম্পূর্ণ ভুল! স্লাইডের পেজ ২১ অনুযায়ী: "A primary key is a unique key that also cannot be null, while a unique key enforces uniqueness but allows nulls."

2.4 Generalization vs Specialization 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে সরাসরি উল্লেখিত: "Generalization vs specialization"। পরীক্ষায় এদের সংজ্ঞা, টপ-ডাউন বনাম বটম-আপ ডিজাইন এবং ISA ট্রায়াঙ্গল ডায়াগ্রাম বাধ্যতামূলক।

সহজ ভাষায় কনসেপ্ট (Beginner Explanation)

চলো আগে বুঝি জিনিসটা আসলে কী:
• Specialization (টপ-ডাউন অ্যাপ্রোচ): একটা বড় সাধারণ এনটিটিকে ভেঙে ছোট ছোট বিশেষায়িত এনটিটিতে রূপান্তর করা। যেমন: ব্যাংকের Person এনটিটিকে ভেঙে আমরা পেলাম Employee এবং Customer। আবার Employee-কে আরও ভেঙে পেলাম Officer, Teller, Secretary। ওপর থেকে নিচে নামছে—তাই এটি Top-Down!
• Generalization (বটম-আপ অ্যাপ্রোচ): একাধিক এনটিটির কমন বৈশিষ্ট্যগুলো খুঁজে বের করে তাদের ওপর একটা বড় সুপার-ক্লাস তৈরি করা। যেমন: Savings_Account এবং Current_Account-এর কমন বৈশিষ্ট্য মিলিয়ে তৈরি হলো Account। নিচ থেকে ওপরে উঠছে—তাই এটি Bottom-Up!
• Attribute Inheritance: নিচের স্তরের (Subclass) এনটিটি স্বয়ংক্রিয়ভাবে ওপরের স্তরের (Superclass) সব অ্যাট্রিবিউট পায়। যেমন: Employee স্বয়ংক্রিয়ভাবেই Person-এর name, street, city পেয়ে যায়।

Generalization Design Constraints (Source: 2nd Chapter-1.pdf, Page 26)

  • Disjoint vs Overlapping:
    • Disjoint: একজন ব্যক্তি একই সাথে কেবল একটি সাব-এনটিটির সদস্য হতে পারে (যেমন: একজন কর্মকর্তা একই সাথে টেলর ও সেক্রেটারি হতে পারবেন না)। ER ডায়াগ্রামে ISA ট্রায়াঙ্গলের পাশে disjoint লেখা থাকে।
    • Overlapping: একজন ব্যক্তি একই সাথে একাধিক সাব-এনটিটির সদস্য হতে পারে (যেমন: একজন ব্যক্তি একই ব্যাংকের Employee এবং একই সাথে Customer হতে পারেন)।
  • Completeness Constraint (Total vs Partial):
    • Total: হায়ার-লেভেলের প্রতিটি এনটিটিকে অবশ্যই অন্তত একটি লোয়ার-লেভেল এনটিটিতে অন্তর্ভুক্ত হতে হবে (ডাবল লাইন দিয়ে নির্দেশিত)।
    • Partial: হায়ার-লেভেলের কিছু এনটিটি কোনো লোয়ার-লেভেলে নাও থাকতে পারে (সিঙ্গেল লাইন)।

2.5 Ternary to Binary Relationship Conversion (The 3 Slide Patterns) 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে লাল কালি দিয়ে বিশেষ গুরুত্ব দেওয়া: "Ternary to Binary (slide এর ৩টি)"। লেকচার স্লাইডের ৩৯, ৪০ এবং ৪১ পাতায় টার্নারি রিলেশনশিপকে বাইনারিতে রূপান্তর করার ৩টি নির্দিষ্ট মডেল দেখানো আছে। পরীক্ষায় ডায়াগ্রামসহ এটি হুবহু আঁকতে আসে!

টার্নারি রিলেশনশিপ কী এবং কেন কনভার্ট করতে হয়?

চলো আগে বুঝি জিনিসটা আসলে কী:
যখন একটি মাত্র রিলেশনশিপে তিনটি ভিন্ন ভিন্ন এনটিটি যুক্ত থাকে, তখন তাকে বলে Ternary Relationship (Degree 3)।
সমস্যা: রিলেশনাল ডেটাবেজ ম্যানেজমেন্ট সিস্টেমে (RDBMS) ৩টি এনটিটিকে সরাসরি ২ মাত্রার টেবিলে রূপান্তর করা খুবই জটিল এবং এতে প্রচুর রিডান্ডেন্সি তৈরি হয়। তাই সফটওয়্যার ডিজাইনাররা টার্নারিকে বাইনারিতে (Degree 2) রূপান্তর করে নেন।
তোমার স্লাইডে ৩টি বিশেষ প্যাটার্ন শেখানো হয়েছে—চলো ৩টিই নিখুঁতভাবে শিখি:

প্যাটার্ন ১: Weak Entity Approach (Slide 39 — Supplier-Part-Project)

2.6 Reduction of ER Schema to Relational Tables 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে সরাসরি উল্লেখিত: "ER to table"। একটি ই-আর ডায়াগ্রামের বিভিন্ন কম্পোনেন্ট (Strong Entity, Weak Entity, Composite Attribute, Multivalued Attribute, M:N Relationship) কীভাবে রিলেশনাল টেবিলে ম্যাপ হয় তা প্রতি পরীক্ষায় লিখিত অংশে আসে।

Slide-by-Slide Reduction Rules (Source: 2nd Chapter-1.pdf, Pages 32–36)

নিয়ম ১: Strong Entity Set Reduction (Page 32)

একটি সাধারণ স্ট্রং এনটিটি সেট সরাসরি একটি টেবিলে রূপান্তরিত হয়, যার কলামগুলো হবে এনটিটির সমস্ত সাধারণ অ্যাট্রিবিউট এবং প্রাইমারি কি থাকবে আন্ডারলাইন করা।
Example: Customer(customer_id, customer_name, customer_street, customer_city)

নিয়ম ২: Composite and Multivalued Attributes (Page 33)

• Composite Attributes: কম্পোজিট অ্যাট্রিবিউট মূল টেবিলে ভেঙে ফ্ল্যাট (flattened) করা হয়। যেমন name(first_name, last_name) হয়ে যাবে মূল টেবিলে দুটি কলাম: name_first_name এবং name_last_name।
• Multivalued Attribute: মাল্টিভ্যালুড অ্যাট্রিবিউটের জন্য সম্পূর্ণ আলাদা একটি নতুন টেবিল তৈরি করতে হয়! নতুন টেবিলের কলাম হবে: (মূল এনটিটির Primary Key + Multivalued Attribute)।
স্লাইড উদাহরণ: Employee এর মাল্টিভ্যালুড অ্যাট্রিবিউট dependent_names এর জন্য টেবিল হবে: employee_dependent_names(employee_id, dname)।

নিয়ম ৩: Weak Entity Set Reduction (Page 34)

উইক এনটিটি সেট টেবিলে রূপান্তরের সময় তার নিজস্ব ডিসক্রিমিনেটর ছাড়াও আইডেন্টিফায়িং স্ট্রং এনটিটির প্রাইমারি কি-কে ফরেন কি হিসেবে যুক্ত করতে হয়।
স্লাইড উদাহরণ: payment(loan_number, payment_number, payment_date, payment_amount) যেখানে loan_number হলো স্ট্রং এনটিটি loan-এর প্রাইমারি কি।

নিয়ম ৪: Relationship Sets Reduction (Pages 34–35)

• Many-to-Many (M:N): উভয় এনটিটি সেটের প্রাইমারি কি এবং রিলেশনশিপের বর্ণনামূলক অ্যাট্রিবিউট নিয়ে একটি আলাদা নতুন টেবিল গঠিত হয়। যেমন borrower(customer_id, loan_number)।
• One-to-Many (1:M): কোনো আলাদা টেবিল করার প্রয়োজন নেই (Redundancy পরিহারের জন্য)। "Many" সাইডের টেবিলে "One" সাইডের প্রাইমারি কি-কে Foreign Key হিসেবে যোগ করে দিলেই চলে!

3.1 Selection (σ) vs Projection (π) Operators 🔴 HIGH PRIORITY

🔴 EXAM ALERT

সাজেশনে সরাসরি প্রশ্ন হিসেবে লিখিত: "Selection vs Projection operator"। পরীক্ষায় এদের প্রতীক, অপারেশনের ধরন (Horizontal vs Vertical), সিনট্যাক্স এবং ডুপ্লিকেট এলিমিনেশন নিয়ে প্রশ্ন থাকবেই।

সহজ ভাষায় কনসেপ্ট (Beginner Explanation)

চলো আগে বুঝি জিনিসটা আসলে কী:
একটি রিলেশনাল টেবিল তো সারি (Row/Tuple) এবং কলাম (Column/Attribute) দিয়ে তৈরি, তাই না?
• Selection (σ): তুমি যদি কোনো শর্ত দিয়ে নির্দিষ্ট কিছু সারি (Rows) ফিল্টার করে আনতে চাও, তখন ব্যবহার করবে Selection। এটা টেবিলকে আনুভূমিকভাবে কাটে—তাই একে বলে Horizontal Subset!
• Projection (π): তুমি যদি কোনো টেবিলের সব কলাম না চেয়ে নির্দিষ্ট কিছু কলাম (Columns) দেখতে চাও, তখন ব্যবহার করবে Projection। এটা টেবিলকে লম্বালম্বিভাবে কাটে—তাই একে বলে Vertical Subset!
মজার বিষয়: প্রজেকশন করার পর যদি দুটি হুবহু একই রকম রো চলে আসে, রিলেশনাল অ্যালজেব্রা স্বয়ংক্রিয়ভাবে ডুপ্লিকেট রো মুছে দিয়ে ইউনিক রো রাখে!
Feature / Dimension Selection Operator (σ) Projection Operator (π)
Symbol & Notation Greek letter Sigma: σpredicate(Relation) Greek letter Pi: πattribute_list(Relation)
Filtering Plane Horizontal Subset: Selects a subset of tuples (rows) that satisfy a given selection condition. Vertical Subset: Selects specified attributes (columns) and eliminates all other unmentioned columns.
Arity (Number of Columns) Output relation has the exact same arity/degree as the input relation. Output relation has arity equal to the number of attributes in the projection list.
Duplicate Elimination No duplicate removal needed (input was a valid relation of distinct tuples). Automatically eliminates duplicate tuples resulting from column omission.

3.2 Cartesian Product (×) & Rename (ρ) Operations 🟡 MEDIUM PRIORITY

Source: 3.Relational_Aljebra.pdf (Pages 5, 11)

Cartesian Product ($r \times s$): যদি রিলেশন $r$-এর ডিগ্রি হয় $p$ এবং টাপল সংখ্যা হয় $n_1$, এবং রিলেশন $s$-এর ডিগ্রি হয় $q$ এবং টাপল সংখ্যা হয় $n_2$; তবে তাদের ক্রস প্রোডাক্ট $r \times s$-এর:
• ডিগ্রি (Columns) হবে = $p + q$
• কার্ডিনালিটি (Rows) হবে = $n_1 \times n_2$।
এটি রিলেশন $r$-এর প্রতিটি টাপলের সাথে রিলেশন $s$-এর প্রতিটি টাপলকে জোড়া লাগিয়ে কনক্যাটেনেশন তৈরি করে।

Rename Operation ($\rho$): রিলেশনাল অ্যালজেব্রার এক্সপ্রেশনের ফলাফলকে কোনো নাম দিতে বা একই টেবিলকে নিজের সাথে তুলনা করতে রিনেম অপারেটর ব্যবহৃত হয়।
• $\rho_X(E)$ : ফলাফল এক্সপ্রেশন $E$-কে নতুন নাম $X$ দেয়।
• $\rho_{X(A_1, A_2, \dots, A_n)}(E)$ : টেবিলের নাম $X$ করার সাথে সাথে তার অ্যাট্রিবিউটগুলোর নাম যথাক্রমে $A_1, A_2, \dots$ এ পরিবর্তন করে।

3.3 Set Operations: Union, Difference, and Intersection 🟡 MEDIUM PRIORITY

Source: 3.Relational_Aljebra.pdf (Pages 7–16)
⚡ UNION COMPATIBILITY RULE

Union ($r \cup s$), Intersection ($r \cap s$), এবং Set Difference ($r - s$) করার জন্য দুটি রিলেশনকে অবশ্যই Union Compatible হতে হবে। অর্থাৎ:
১. উভয় রিলেশনের অ্যাট্রিবিউট সংখ্যা (Arity) হুবহু সমান হতে হবে।
২. বাম থেকে ডানে সংশ্লিষ্ট অ্যাট্রিবিউটগুলোর ডেটা ডোমেইন (Data Types) কম্প্যাটিবল হতে হবে।

• Set Union ($r \cup s$): উভয় রিলেশনের সমস্ত টাপল অন্তর্ভুক্ত করে কিন্তু কোনো ডুপ্লিকেট পুনরাবৃত্তি হতে দেয় না।
• Set Difference ($r - s$): যে সমস্ত টাপল $r$-এ আছে কিন্তু $s$-এ নেই, তাদের বের করে।
• Set Intersection ($r \cap s$): উভয় রিলেশনে উপস্থিত কমন টাপলসমূহ নির্বাচন করে ($r \cap s = r - (r - s)$)।

3.4 Natural Join (⨝) & Outer Joins (⟕, ⟖, ⟗) 🔴 HIGH PRIORITY

Source: 3.Relational_Aljebra.pdf (Pages 15–20)

Natural Join ($r \bowtie s$):
ন্যাচারাল জয়েন হলো দুটি টেবিলের এমন একটি অপারেশন যা:
১. প্রথমে তাদের কার্টেসিয়ান প্রোডাক্ট ($r \times s$) করে,
২. যে সমস্ত অ্যাট্রিবিউট উভয় রিলেশনে কমন আছে তাদের মধ্যে সমতা পরীক্ষা করে ($\sigma_{r.A = s.A}$),
৩. এবং ফলাফলে ডুপ্লিকেট কলাম একবার রেখে অতিরিক্ত কলামটি বাদ দিয়ে প্রজেকশন করে।
r ⨝ s = Πr.A, r.B, r.C, s.E ( σr.B = s.B ∧ r.D = s.D (r × s) )

Outer Joins (Avoiding Loss of Information with NULLs)

Join Type Notation Behavior with Unmatched Tuples
Left Outer Join r ⟕ s Computes natural join and keeps all tuples from the left relation $r$, padding right attributes with NULL if no match exists.
Right Outer Join r ⟖ s Computes natural join and keeps all tuples from the right relation $s$, padding left attributes with NULL if no match exists.
Full Outer Join r ⟗ s Preserves all unmatched tuples from both relations, padding non-matching sides with NULL.

সহজ ভাষায় কনসেপ্ট (Beginner Explanation)

১. PRIMARY KEY: টেবিলের প্রতিটি সারিকে ইউনিকভাবে শনাক্ত করে। এতে কোনো ডুপ্লিকেট মান ঢুকবে না এবং এটি কখনো ফাঁকা (NULL) হতে পারবে না।
২. NOT NULL: ইউজার ডেটা এন্ট্রি করার সময় এই কলামটি কোনোভাবেই ফাঁকা রেখে যেতে পারবে না (বাধ্যতামূলক ফিল্ড)।

4.2 Foreign Key Constraints & ON DELETE CASCADE 🔴 HIGH PRIORITY

Source: Corrected_MySQL.pdf (Pages 25–27)
Formal Definition & Rules (Source: Corrected_MySQL.pdf, Page 25)
"A Foreign key constraint is used to create a relationship among different tables. Primary key of one table (Parent/Master) and foreign key of another table (Child) are used to create this relationship."

Rules of Foreign Key Constraint (Must Memorize):

  1. Referential Integrity: If a value does not exist in the master (parent) table, no insert or update operation referencing that value can be performed on the foreign (child) table.
  2. ON DELETE CASCADE: If you specify the ON DELETE CASCADE option, deleting a record from the master table will automatically delete all corresponding child records from the foreign table!
  3. Data Type Matching: The primary key column in the parent table and the foreign key column in the child table must be of the exact same data type and compatible size.
-- Creating Parent Table
CREATE TABLE department (
    dept_id INT NOT NULL,
    dept_name VARCHAR(30) NOT NULL,
    PRIMARY KEY (dept_id)
);

-- Creating Child Table with FOREIGN KEY and ON DELETE CASCADE
CREATE TABLE employee (
    emp_id INT NOT NULL,
    emp_name VARCHAR(40) NOT NULL,
    salary DOUBLE NOT NULL CHECK (salary > 0),
    dept_id INT NOT NULL,
    PRIMARY KEY (emp_id),
    FOREIGN KEY (dept_id) REFERENCES department(dept_id)
        ON DELETE CASCADE
        ON UPDATE CASCADE
);

1. Must-Memorize Definitions

DBMS: Interrelated data collection + software programs to access data conveniently and efficiently.
Weak Entity Set: An entity set lacking a primary key, existence-dependent on an identifying strong entity via an identifying relationship.
Candidate Key: A minimal super key having no redundant attributes, capable of uniquely identifying every tuple.
Selection (σ): Unary operator producing a horizontal subset of tuples satisfying a given predicate.
Projection (π): Unary operator producing a vertical subset of specified attributes with automatic duplicate tuple removal.
Specialization: Top-down design designating distinctive lower-level entity sets with inherited attributes via ISA component.

2. High-Yield Differences in 1 Line

  • Primary Key vs Unique Key: PK cannot accept any NULL and only 1 per table; Unique Key accepts NULL and multiple are allowed.
  • Super Key vs Candidate Key: Super Key may contain redundant columns; Candidate Key is strictly minimal with zero redundancy.
  • Strong vs Weak Entity: Strong entity has a PK (single rectangle); Weak entity has only a partial key/discriminator (double rectangle).
  • 2-Tier vs 3-Tier: 2-Tier connects client directly to DB via ODBC/JDBC; 3-Tier routes requests through an intermediate Application Server.
  • Selection vs Projection: Selection filters rows (horizontal); Projection filters columns and eliminates duplicates (vertical).
  • Specialization vs Generalization: Specialization is top-down; Generalization is bottom-up.
